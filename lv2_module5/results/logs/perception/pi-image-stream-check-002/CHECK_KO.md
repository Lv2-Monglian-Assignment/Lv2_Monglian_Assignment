# Pi 로컬 영상 연속 관측 검토

## 실험 환경

D435 컬러 요청 프로파일 RGB8 320×240·6Hz, Pi ROS Lyrical·Cyclone DDS·DOMAIN 30이다. 카메라를 유지한 두 번째 Pi 로컬 관측이다. 이전 PC 검출 프로세스 45277은 읽기 전용 프로세스 조회에서 계속 실행 중이었다.

## 실험 목적

발제 문제 2의 영상 입력 → /target 경로에서 PC 전달 이전의 Pi Image 도착을 확인한다.

## 계획한 방법

동일 코드·설정으로 Pi 내부 Image를 10초 관측하고 원본 메타데이터와 소스를 대조한다.

## 실제 수행 방법

PC 확인창에서 SSH 관측 명령을 터미널에 직접 입력했다. 이후 원본 result.json과 observe_source.py를 읽기 전용으로 복사해 대조했다. 파일 조회·기록 정리는 Codex로 수행했고 새 ROS 측정은 대신 실행하지 않았다.

## 확인 결과

| 항목 | 관측값 |
|---|---:|
| Image 수 | 32개 |
| 실제 관측 시간 | 10.00084초 |
| 첫 도착 | 시작 후 0.47890초 |
| 마지막 도착 | 시작 후 9.78204초 |
| 첫·마지막 도착 사이 빈도 | 3.33221Hz |
| 받은 header stamp 간격으로 계산한 빈도 | 3.71171Hz |
| 최대 도착 간격 | 0.60106초 |
| 최대 관측 stamp 간격 | 0.50112초 |

형식은 320×240 rgb8, frame_id는 camera_color_optical_frame이며 관측 stamp는 단조 증가했다. 호스트의 IP 재조립 실패·시간 초과 및 UDP 수신 오류·버퍼 오류 누적 차분은 모두 0이다. 원본 status=complete, error=null이며 로컬·원격 저장 소스·결과 소스 해시는 일치한다.

## 해석 및 한계

이번 관측은 첫 도착이 종료 직전이었던 첫 시험과 구별한다. Pi 내부 구독에서도 요청 6Hz와 다른 관측 빈도가 나왔다. 따라서 PC로 전달하는 구간만 문제라고 가정해 설정을 바꾸지 않는다. 이 구독은 best-effort/depth 1이며 Pi 발행·DDS 수신·관측 실행의 영향을 포함한다. 수신되지 않은 프레임 수와 물리 카메라 생성 FPS는 확정하지 않는다. 호스트 커널 오류 차분 0은 DDS·응용 계층 손실 없음이나 전체 영상 정상의 증명이 아니다. 이전 PC 관측과 시점·카메라 프로세스가 다르므로 27/32를 전달 성공률로 계산하지 않는다. 도착 시간과 source stamp는 서로 다른 시계 기준이며 두 빈도 차이의 원인은 미확정이다.

다음 비교는 카메라·프로파일·Pi 관측 코드를 유지하고 PC target_detector만 잠시 중단한 조건이다. 먼저 PC 검출 실행창에서 Ctrl+C 키를 눌러 정상 중단하고 PC 확인창에서 해당 프로세스가 사라졌는지 확인한다. 중단 확인 후 별도 단계로 Pi image-stream-check-003 관측을 직접 입력한다. PC로의 Image 구독을 제거한 조건 비교이며 속도 개선 시에도 Wi-Fi를 유일한 원인으로 단정하지 않는다. 계획만 준비했고 중단·추가 관측 결과는 아직 없다.

전체 진행률은 기존 증거 확인 5/7, 약 71%다. 현재 연속 수신 안정성과 근본 원인은 미검증이다.
