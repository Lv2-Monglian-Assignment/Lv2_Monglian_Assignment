# 파라미터 실험 1 — 축소 검출 `detect_scale` 1.0 대 0.5 (2026-10-08)

- 목적: Pi 4에서 검출용 사본을 0.5배(320×240)로 줄였을 때 검출 결과가 같은지, 처리 시간이 얼마나 주는지 확인해 `detect_scale` 값을 정한다.
- 장비·코드: Raspberry Pi 4 (pa23), OpenCV 4.10.0, 커밋 `f910df2`. 모터 사용 안 함(브리지 미실행). `config/`는 바꾸지 않고 복사본의 `detect_scale`만 바꿨다.
- 판정 기준 (시험 전 확정): 0.5의 검출(목표 있음 30장)·오검출(목표 없음 10장)이 1.0과 같고, 둘 다 검출한 프레임의 |ex 차이|·|ey 차이| 평균 < 0.005, 실시간 평균 `proc_ms`가 20 % 이상 감소, 실시간 검출 비율이 1 %p 넘게 낮지 않으면 0.5 채택을 제안한다. 검출이 떨어지면 1.0 유지.

## 1-2. 실시간 (카메라 + 검출 노드, 미리보기 끔)

- 장면: 파란 원기둥 1개, 카메라에서 약 0.43 m(깊이 평균), 화면 오른쪽(ex 약 +0.57), 다른 파란 물체 없음. 두 측정 사이에 물체·카메라를 움직이지 않음.
- 실행 (Pi): `bash results/param_experiments/detect_scale/run_live.sh <scale> <폴더>` (1.0 → 0.5, 각각 시작 후 5 s 버리고 약 40 s), `python3 results/param_experiments/detect_scale/analyze_live.py <폴더>`. ROS_DOMAIN_ID 77
- 결과: [live_20261008_165141/](live_20261008_165141/) (검출 기록 CSV 2개, `top_*.txt`, `run_*.txt`, `summary.json`, 사용한 설정 복사본)

- 처리 FPS는 두 설정 모두 카메라 입력(30 fps)에 막혀 같다. 그래서 처리 시간(`proc_ms`)으로 비교했다.
- `proc_ms`는 영상 변환·검출·깊이·발행까지 포함한 한 프레임 처리 시간이다(1-1은 검출 함수만).
- 1.0 측정 시작 때 카메라 드라이버가 깊이 스트림 시작 오류를 한 번 보고했으나, 측정 구간의 깊이는 모두 유효했다.
- 온도는 `vcgencmd`가 권한 오류여서 `/sys/class/thermal/thermal_zone0/temp`로 쟀다.

## 한계

- 같은 프레임 40장은 목표 면적 4,196~4,286 px²(가까운 거리 한 범위)이고, 실시간도 약 0.43 m 한 장면이다. 목표가 작아지는 먼 거리(1.0 m 이상)는 확인하지 않았다. 0.5에서는 마스크·형태학 커널이 같이 줄어 작은 목표가 먼저 사라질 수 있다.
- 0.5의 면적비가 평균 1.6 % 작다(축소 마스크의 경계). 크기 검증(cm²)의 하한·상한에 그만큼 덜 여유가 있다.
- 각 설정 1회 측정이다. 0.5 측정이 1.0 뒤에 이어져 시작 온도가 5.4 °C 높았다.

## 최종 판단 (실험 5의 먼 거리 비교 반영)

- 실험 5에서 세운 블록을 1.19·1.68·2.15 m에 두고 1.0과 0.5를 같은 장면에서 쟀다. 1.19·1.68 m는 둘 다 100 % 검출했지만, **2.15 m에서 0.5는 8.5 %(1.0은 100 %)**로 떨어졌다. 0.5의 블록 화면 면적이 1.0보다 9~16 % 작게 나와 최소 면적 100 px² 아래로 떨어진 것으로 본다. ([실험 5](../min_area/summary.md))
- 판정 기준 "검출이 1.0과 같음"을 먼 거리에서 충족하지 못했고, 1.0에서도 처리 FPS가 카메라 입력(30 fps)과 같아 0.5의 이득은 CPU 여유뿐이므로 **`detect_scale` 1.0 유지를 제안**한다.
